仓库内可阅读的实现文档与测试链接列在各阶段后。原始记录的脱敏摘要、证据等级和散列见 [证据索引](history-evidence.json)。散列用于日后与本地原件核对，不代替原始日志，也不证明记录中的全部结论。个人路径、凭据、完整会话、原始任务正文和运行日志未上传。

## 1. 从 Kether 角色设计到宿主可执行的治理

早期资料来自用户维护的 Kether 预设及角色技能。Kether 保留意图和授权，Tifereth 协调执行，Yesod 规范化需求，Binah 澄清，Hod 分类，Malkuth 侦察，Chochmah 规划，Geburah 审查，Chesed 实现，Netzach 验证，Da'at 处理能力桥接。

移植保留的是这些责任、变更前后审查、默认单写者、有限修复和证据验收。DSH 预设中的专用执行契约、worker-thread、隔离工作流引擎、提交事务和消息确认协议，需要相应运行时，不能通过 Markdown 技能自动获得。

随后工作流适配了宿主的真实能力与授权：简单任务使用主代理紧凑路径；复杂任务只有在有独立价值时才进行有限委派；已有的可逆操作授权不再被机械地转化为额外确认步骤。主代理始终负责整合和最终验收。

来源：[预设来源与适配说明](../payload/workflow-skills/kether-governance/references/source-mapping.md)、[历史 DSH 契约参考](../payload/workflow-skills/kether-governance/references/dsh-contract.md)。后者是历史参考，不能直接用于当前 Pi 调用。

## 2. 2026-09-04：迁移到 Pi 直连

有明确日期的迁移报告将有效路径定义为：

```text
ChatGPT Work / Codex → 主代理中的 Kether 治理 → Pi → openai-codex
```

迁移移除了活动执行链对 DSH CLI、Cordis、DSH worker-thread 和 DSH 事务协议的依赖，保留旧预设和报告作为历史资料。角色名称不再被当作执行证据，实际结果需要给出 provider、model、工具调用与错误。

当时的报告记录了 Luna 在 `access=none` 下返回指定确认文本，以及 `target=codex-cli` 在启动子进程前被拒绝。该报告只确认磁盘上的 Codex 规则与技能、Pi 路径和这一次调用；没有证明 ChatGPT 账号个性化设置已同步到所有会话。

这一阶段的 OpenAI 单一路由表述是历史状态。当前规则已明确增加 Sonnet 的审查角色例外，见 [当前路由规则](../templates/agent-references/pi-routing.md)。

## 3. 将治理要求落实到网关边界

后续扩展把部分约束从提示词移到运行时：

- WSL2/Bubblewrap、读写范围检查和资源预算限制每次任务能访问什么、运行多久以及消耗多少资源。
- 请求账本和幂等键处理重连、重放及不确定写入；重叠写锁避免并发修改冲突。
- 调度器分别管理排队与执行期限、资源容量和任务依赖；Provider 熔断区分模型服务与认证故障。
- 确定性结果验证、审计脱敏、异步状态和完整结果导出让验收有结构化依据。
- 安装入口统一为 Init、Plan、Install、Verify、Build，发布范围排除凭据和运行状态。

这些能力的当前实现可直接检查：[执行调度](../payload/pi-dispatch/extensions/admission-scheduler.js)、[请求账本](../payload/pi-dispatch/extensions/request-ledger.js)、[写锁](../payload/pi-dispatch/extensions/write-scope-locks.js)、[沙箱入口](../payload/pi-dispatch/sandbox/pi-kether-sandbox)、[安装入口](../Workflow.ps1)。现存材料不足以为这些模块逐一指定首次实现日。

直接 LSP 是这一阶段的重要分离：结构化查询直接执行，不调用模型，也不依赖模型认证。历史实测覆盖 Python diagnostics、hover 和结构搜索；返回 `modelCalls: 0`。初期诊断曾因语言服务器未初始化而退化为 Tree-sitter，之后补齐启动、打开文档和等待诊断发布。Tree-sitter 只能证明语法或结构信息；单文件快照也不能证明完整跨文件语义分析。见 [直接 LSP 规则](../templates/agent-references/pi-lsp.md)。

## 4. 2026-09-16：契约、证据和认证分层

角色契约 v2 为不同角色定义了类型化 deliverable。链接任务还必须携带成功前驱的请求 ID、角色、阶段和结果摘要；网关验证这些关系并加载前驱结果。standalone 任务仍可用于独立小任务，但不能冒充完整阶段链。

H04 记录了 114 项测试通过，同时明确记录真实 scout 因 `refresh_token_reused` 认证错误失败，因此未建立成功的后续链。这个失败是历史的一部分。契约验证能证明结构和衔接条件，不能证明模型陈述正确，也不能证明宿主内部确实执行了所有治理步骤。见 [角色契约 v2](../payload/pi-dispatch/ROLE-CONTRACTS-V2.md)。

异步执行补充了完整结果导出、脱敏后分页、结果散列和认证、启动、首响应、生成、进程收尾、清理等计时。连接器当时曾缺少新工具，必须区分网关已实现与当前会话已可调用；结果也不是无限期保存，网关重启或记录淘汰后可能无法取回。见 [异步结果与计时](../payload/pi-dispatch/ASYNC-RESULTS-AND-TIMINGS.md)。

认证逐步迁移到宿主维护，沙箱只接收临时访问令牌。Claude 续期后仍需显式恢复探针；OpenAI 持久化修复记录了重启读取与权限保持。H06 对应的心跳因宿主内存准入而取消，未实际调用模型，不能写成模型验证通过。多次独立审查达到执行时限，也没有被记为批准。见 [认证更新](../payload/pi-dispatch/AUTH-RENEWAL.md)。

## 5. 2026-09-17 至 09-18：运行环境与编辑器边界

历史回顾记录了 Windows 将 7331 纳入保留端口区间后，服务启动遇到拒绝绑定；配置迁移到 17331，并增加端口预检、按阶段脱敏的启动日志和进程提前退出检查。验收从“启动脚本输出成功”变为端口、进程、healthz、readyz、Tunnel 和真实调用逐层验证。9 月 17 日的 Luna 只读无工具任务通过，证明了当时的单任务路径。此段依据 H13 的历史归档回顾，本次没有重演旧端口故障。

监控也从任务列表扩展到阶段计时和桌面状态过渡。归档记载透明 WPF 窗口直接动画化尺寸会阻塞布局，修复选择先完成布局，再动画化透明度和视觉缩放；快速请求合并为最新状态。相关代码见 [桌面监控](../payload/pi-dispatch/pi-extensions/desktop-monitor/README.md)。

9 月 18 日的编辑器扩展将固定 Unity/Blender 操作接入受控通道：主代理授予精确参数和操作 ID，任务通过专用 IPC 使用授权能力，写入需要场景前置条件和持久化重放保护。普通无工具任务不会自动获得编辑器权限。

H08 的真实 WSL 验收覆盖两个编辑器的只读查询、角色结果和清理；隔离 Blender 场景验证覆盖部分写入与导出；Unity 变更模板在提前返回模式下完成编译，不能据此宣称真实修改成功。编辑器副作用发生在宿主，不能由 WSL 文件快照回滚。见 [编辑器授权](../payload/pi-dispatch/EDITOR-AUTHORIZATION.md)。

## 6. 2026-09-18：从规则集合走向可管理的模块

全局 AGENTS 被整理为精简入口和按触发条件读取的 references。拆分降低了每次加载的协议细节量，没有降低原有角色绑定、契约、审批或证据要求。发布安装器随后补齐引用文件的安装、旧规则备份和无关文件保留行为。

关于 Astra 提示词指南及 Cordis 的讨论促成了对职责、上下文和扩展边界的重新检查。本仓库没有收录足以复原正式 Astra 指南逐项比对的材料，因此不声称获得官方兼容认证。

生命周期强化增加了八个命名模块及其依赖和所有权：audit、circuit、ledger、writeLocks、taskMonitor、dispatch、lsp、executor。启动前检查重复名称、缺失依赖和循环；部分启动失败时回收已获得资源；关闭按依赖逆序执行，并汇总清理失败。

运行时替换只开放 dispatch 和 LSP 适配器，且仅限可信宿主在没有在途、排队或待执行工作的情况下调用。候选初始化失败可以回退，旧适配器释放失败则停止接纳工作。账本、锁、熔断和队列等有状态服务保持固定。工厂是同步接口，清理可以异步，但任意挂起的清理函数不能被安全强制取消。

这使 YHWH 具备明确的依赖、资源回收和有限替换机制；其执行链仍不加载 Cordis，也没有实现 Cordis 的完整通用插件体系、任意插件热装载或有状态服务迁移。这里描述的是本仓库的实现范围，不能据此推断它与上游 Cordis 在功能上等价。详见 [生命周期接口及限制](../payload/pi-dispatch/MODULE-LIFECYCLE.md)。

H09 记录了 20 个新增行为测试与 80 项相关测试通过。一次并行测试中的既有 HTTP 检查失败，后续串行通过，但根因未确定；侦察超时和被拦截的独立审查没有被算作成功。部署是后续单独授权的动作，H10 记录了重启、健康/就绪检查及 Luna、Sonnet 心跳通过。该心跳没有验证真实运行中的适配器迁移。

## 持续保留的架构决定

| 决定 | 原因 | 仍需遵守的限制 |
| --- | --- | --- |
| 主代理拥有授权、整合和验收 | 跨任务保持用户意图和最终责任 | 内部主代理步骤不等于已被 Pi 证明的阶段 |
| 模型委派有限，确定性操作直接执行 | 将推理与可重复检查分开 | 不因可用就增加代理调用，也不把结构搜索等同语义分析 |
| worker/reviewer 路由显式绑定 | 使执行来源与角色职责可追踪 | 不通过换模型、换角色绕开能力或认证阻断 |
| 凭据刷新留在宿主 | 降低沙箱和任务结果接触长期凭据的范围 | 模型网络访问和宿主依赖仍是实际运行边界 |
| 账本与写锁保持有状态连续性 | 处理重试、重复写入及不确定结果 | 结果丢失不授权再次执行写任务 |
| 仅空闲时替换有限适配器 | 提供替换能力而保持已有任务和状态完整 | 不提供任意插件加载、有状态热迁移或无限清理保证 |
| 历史失败与证据缺口持续保留 | 避免把后来的成功追溯成早先通过 | 测试、心跳、安装、完整治理链分别验收 |

## 归属与后续记录

用户提出了工作流目标、治理偏好、模型绑定、生命周期强化和发布要求；本项目在 AI 辅助下完成检查、实现、测试与文档整理。Kether 角色组织来源于用户的既有预设，Pi、DSH/Cordis 及其他第三方组件的名称和实现归各自项目；不能把它们的全部能力归为 YHWH 的原创贡献。第三方说明见 [THIRD_PARTY.md](../THIRD_PARTY.md)。

后续新增里程碑应链接真实提交和验证材料，区分代码实现、已部署、模型心跳、独立审查和完整工作流验收。尚未发生的扩展保留为计划，不写入已完成历史。
