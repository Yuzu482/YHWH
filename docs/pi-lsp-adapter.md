# YHWH 自有 Pi LSP 适配插件

[English](pi-lsp-adapter.en.md)

`yhwh-pi-lsp` 1.6.0 是 YHWH 自有 Apache-2.0 适配层，将现有 multilspy 探针接入受管 Pi 工作代理。它不是微软发布的 Pi 插件，也没有移除旧扩展的全部依赖。

## 使用范围

安装器将插件和可信通道安装到 WSL。`access:read` 和 `access:workspace-write` 的受管任务自动加载插件；`access:none` 的审查者不加载、不获得新工具。主 Agent 原有的 `lsp_request` 入口保持不变。

| 工具 | 用途 |
| --- | --- |
| `yhwh_lsp_diagnostics` | 当前文件诊断 |
| `yhwh_lsp_hover` | 悬停类型和说明 |
| `yhwh_lsp_definition` | 定义位置 |
| `yhwh_lsp_references` | 引用位置 |
| `yhwh_lsp_symbols` | 文件符号；可按名称精确过滤 |
| `yhwh_lsp_completions` | 补全建议 |
| `yhwh_lsp_code_actions` | 代码操作建议，不执行编辑或命令 |

参数为 `path`，定位查询另外提供成对的 `line`、`character`，或者唯一精确符号 `query`。位置为 1-based UTF-16。不接受用户命令、服务地址、凭据、环境覆盖或任意工作区根目录。路径必须属于本任务已准入的工作区快照。

例如：`yhwh_lsp_diagnostics({"path":"src/main.ts"})`；`yhwh_lsp_hover({"path":"src/main.ts","line":3,"character":8})`。

插件仅适用于 YHWH 管理的 WSL Pi 任务。在任意宿主 Pi 会话中单独加载包不会建立可信通道；缺少通道明确报错，不回退到非隔离进程。无须给插件配置 API key。

## 隔离和生命周期

Pi 子进程通过独立 IPC 消息请求可信启动器侧的代理进程。代理必须处于本任务的 CPU、内存、进程数限额 cgroup 中，并从固定任务目录取文件。逐级目录描述符与 `O_NOFOLLOW` 防止符号链接和父目录替换造成越界读取；拒绝特殊文件、超过 4 MiB 或读取期间改变的文件。

同一任务只为一个未变化文件保留服务器，按文件路径和内容 SHA-256 复用。Python 按需保留两个后端：Pyright 提供诊断和代码操作建议，Jedi 提供其余语义查询，交替调用时各自复用；其他语言最多保留一个服务器。每次仍发送真实 LSP 查询，不缓存答案。文件内容或路径变化时，等待全部旧服务器结束，再创建新的只读单文件快照；返回结果前再次读取当前文件并核对哈希，发现变化则明确失败。这样可以读取代理刚完成的修改，不接受旧版本诊断。

语言服务器在独立 PID/网络命名空间、清空的环境和临时目录中运行，不继承 FD3 凭据。通常使用空 `/proc`；C# 为支持 .NET、Go 为读取 gopls 自身可执行文件，使用仅可见探针自身 PID 命名空间的只读 `/proc`，不能查看宿主进程。探针与父模型任务共享总资源预算，不向网关申请第二个任务槽位。Python 双后端会增加内存占用，但不提高任务资源上限。每个后端空闲 15 秒后独立关闭；查询失败、取消和任务结束会关闭并清理全部后端，不跨任务共享。单次查询限时 60 秒，插件通道等待上限 70 秒；任务自身较短的总限时仍优先。插件最多排队四项、串行执行；每任务最多接受 64 个探针请求。

复用中的结果返回 `serverSession`（内容哈希、会话代次、是否复用、`poolSlot` 和 `poolCapacity`），并明确标记 `serverCleanup.ok:null`、`state:retained-until-session-close`。这表示服务器仍在运行，不能当成已完成清理；启动器在任务结束时等待最终清理，清理失败使任务失败。取消时可终止探针命名空间；会话池清理结果标记 `pool-terminated`，仅全部清理成功才返回 `ok:true`。主 Agent 的直接 `lsp_request` 保持一次一进程及逐次清理的语义。

取消会中止探针，通道关闭会取消未完成请求。无效协议、服务器异常或缺失清理证据不会被当成检查通过。JS/TS 诊断保留三阶段完成证据。结果中的 `modelCalls:0` 仅指该探针，不代表调用它的模型任务没有模型消耗。

C/C++ 使用已安装的 clangd，并复用单个后端。其清理路径等待进程实际退出、读完关闭后的输出管道，替代固定半秒延迟；两秒内未完成则明确报告清理失败，父隔离层仍负责最终回收。此优化降低任务结束、编辑失效重建以及直接探针的清理耗时，不改变 clangd 的诊断或索引配置。Python、JS/TS 等后端的清理实现不变。安装器已声明 clangd 依赖；旧运行时缺失时必须先补齐。单文件快照不包含项目头文件或编译数据库，因此不保证完整项目编译结果。

## 兼容与许可

C# 使用安装器固定版本的 .NET 10 SDK 和 csharp-ls 0.26.0。探针生成仅引用准入 `.cs` 文件的自有最小项目，不加载用户项目配置、外部依赖或自定义构建任务，不进行 NuGet 下载；中间文件只写入 `/tmp`。固定环境关闭遥测、诊断端口和 MSBuild 节点复用，将每个 .NET 进程的托管堆限制为 512 MiB，整个任务仍受原有 cgroup 上限约束。C# 复用单个服务器，并采用实际退出等待清理；进程提前结束会立即返回不可用，不再等满查询超时。首次启动仍有明显成本，文件修改后也要重新启动。该单文件 .NET 10 分析不能证明 Unity 程序集、自定义框架或完整项目编译正确。

原 `lsp_*`、`code_overview`、`ast_search`、`code_rewrite` 等入口暂时保留。任务提示优先使用 `yhwh_lsp_*` 进行单文件语义检查，但不自动把失败检查改成结构分析成功。重命名、项目级符号与跨文件完整性不在本插件新增的保证范围。

本阶段仍安装 pi-lsp-extension，公开发布许可门禁保持阻断。彻底移除旧扩展需要迁移其结构后端和剩余兼容功能，再清理依赖与上游源码片段。详见 [LSP 组件说明](lsp-component.md)。

## 验证

Java 使用固定的 Java 21 与 JDT LS 1.60.0，通过专用启动器设置运行时和共享库路径；只读挂载 JDK 的 `security` 配置目录，不引入管理凭据目录，继续使用空 `/proc` 和无网络沙箱。Eclipse 配置副本、索引和缓存仅放在本次探针的 `/tmp` 中，结束即回收。固定关闭 Maven/Gradle 导入、自动构建及额外引用库，不读取用户构建配置。Java 使用单个可复用服务器、实际退出等待及异常退出即时失败；非项目/不在类路径中的诊断明确返回不可用，不能当成语义检查通过。

Java 探针使用单处理器、Serial GC、64 MiB 初始堆、512 MiB 最大堆及一级 JIT 编译，降低短任务启动与首次索引成本；整个任务仍受既有资源上限约束。此策略面向最多 64 次调用的任务内复用，并非长驻 Java 服务的通用 JVM 建议。首次启动及首次引用查询仍需数秒；编辑后重新启动。单文件与标准库分析不证明 Maven/Gradle、Android 或多模块项目构建正确。

普通回归在 `payload/pi-dispatch` 运行 `npm test`。已配置 WSL 运行时的维护者可运行 `python install/Test-PiLspAdapter.py`：使用真实 Pi SDK 加载插件，经 IPC 和隔离服务器检查七项工具、刚写入文件的可见性、取消、文件范围与无网络只读限制，并清理临时任务。该测试不调用模型、不部署文件，不证明所有语言、全新安装或模型自主选用工具的行为。

加上 `--installed` 可检查已安装运行时的适配器文件；这些文件只会复制到临时测试目录，现有服务不被修改。

加上 `--benchmark` 可交替比较两轮冷启动与复用：每轮依次查询诊断、悬停、符号、定义、引用和诊断，核对完整语义结果相同，并验证真实服务器空闲回收。计时包括启动和最终清理。该单文件 TypeScript 样例不代表所有语言、大型项目或实际模型任务的加速幅度。

加上 `--python-benchmark` 可交替比较两轮 Python 单槽与双后端策略。每轮八次诊断/语义交替查询，断言结果相同、后端复用正确、最多两个快照及最终/空闲清理完成；同时采样整个测试 cgroup 的内存，包括测试进程、服务器和文件缓存。普通真实 SDK 检查也覆盖 Python 双后端复用与编辑后同时失效。这些测试不调用模型，内存和速度不能直接代表完整模型任务或大型项目。

加上 `--cpp-benchmark` 可分别对 C/C++ 交替比较旧清理与实际退出等待：命令、输入和资源限制相同，每轮八次调用覆盖七项工具，核对完整结果相同并采样 cgroup 内存和任务数（含线程）。普通真实 SDK 检查覆盖 C/C++ 七项工具、复用及编辑后错误诊断消失。性能基准包含启动与最终清理，不能解释为已复用查询或编译器分析本身的同等提速。

加上 `--csharp-benchmark` 可对比两轮 C# 旧清理与实际退出等待。两组均包含本次 .NET 兼容修复；每轮八次调用覆盖七项工具，断言会话复用、真实错误诊断和最终清理。补全项中的随机解析句柄先校验 UUID 格式，再从语义比较中排除；其余结果逐项比较。报告启动、查询、清理、整个测试 cgroup 的内存和任务数。普通 SDK 测试另外验证编辑后诊断刷新；隔离测试验证只读私有进程视图、无宿主根目录访问和无网络。这些结果不等同于大型 C# 项目或模型任务的性能保证。

加上 `--java-benchmark` 可交替比较两轮默认分层 JIT 和一级 JIT，每轮八次调用覆盖七项工具。两组都包含相同的 Java 兼容修复、堆上限、单处理器及清理逻辑，只改变 JIT 层级。逐项比较完整结果，断言类型错误诊断、会话复用及最终清理，并报告整个测试 cgroup 的内存和任务数（含线程）。普通 SDK 测试验证 Java 七项工具及修改后诊断刷新，另检查只读安全配置、空 `/proc` 和无网络。上游配置依据见 [JDT LS 初始化处理](https://github.com/eclipse-jdtls/eclipse.jdt.ls/blob/v1.60.0/org.eclipse.jdt.ls.core/src/org/eclipse/jdt/ls/core/internal/handlers/BaseInitHandler.java)与[诊断边界](https://github.com/eclipse-jdtls/eclipse.jdt.ls/blob/v1.60.0/org.eclipse.jdt.ls.core/src/org/eclipse/jdt/ls/core/internal/handlers/DiagnosticsHandler.java)。

### Go 与 Rust 单文件适配

Go 自动使用固定的 Go 1.27.1 / gopls 0.23.0；Rust 自动使用 Rust 1.98.1 / rust-analyzer 1.98.1。两者提供诊断、悬停、定义、引用、符号、补全和代码操作预览，沿用任务内服务器复用、文件修改失效和最终清理。无需模型或 API key。

Go 使用已完成的 `textDocument/diagnostic` 拉取结果，并要求独立的诊断发布证据；固定版本 gopls 的完整结果可能含空 `kind`，只兼容其带 `items` 的已完成响应，不接受 `unchanged`。Go 关闭模块下载、工具链自动下载、工作区配置、cgo、外部包驱动和遥测，使用只读私有 PID 视图供 gopls 读取自身可执行文件。项目外部依赖和多文件模块不在该快照范围内。

Rust 使用固定的 2024 edition 单文件 library crate 与标准库，不读取 Cargo 项目；关闭构建脚本、过程宏、Cargo 检查和实验性分析器诊断。诊断及代码操作请求额外执行有界的 `rustc --emit=metadata` 检查，等待编译器结束并确认回收，再结合语言服务器的发布证据返回。每次诊断重新检查；首次空通知不能直接证明无错误。仅生成临时元数据，不链接或运行用户程序，不代表完整 Cargo 工作区构建通过。诊断坐标按 UTF-8 字节偏移转换为 LSP UTF-16。

探针运行时无网络、无凭据，源文件只读；Rust 继续使用空 `/proc`。初次安装会下载带固定 SHA-256 的官方 Go/Rust 归档，并从官方模块代理校验构建 gopls。新工具链仅安装到受管运行时，不替换宿主 PATH、rustup 或 Go 配置。依赖与通知清单见 [Go/Rust 材料](../licenses/go-rust-runtime.json)。普通 `install/Test-PiLspAdapter.py` 测试包含两种语言的真实七工具调用、错误修正、复用、清理及 Rust 所有权错误；耗时为本机小样本，不是大型项目性能保证。
