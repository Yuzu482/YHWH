# Result durability and backpressure

Failed persistent result writes close new model admission in both dispatch paths. Existing requests are reconciled by their original identity; started models may finish, and sole-copy results are never evicted for count, bytes or TTL. Result reads, cancellation and host verification retain their existing gates. Optional sandbox evidence still cannot replace host evidence.

`resultCache` in capabilities and the monitor reports retained UTF-8 serialized bytes, protected results, pending writes, reservation count, oversized bytes and the non-sensitive degraded reason. `PI_RESULT_STORAGE_UNAVAILABLE`, `PI_RESULT_CACHE_PRESSURE` and `PI_GATEWAY_CLOSED` identify prelaunch refusals. Global lifecycle shutdown retains `GATEWAY_UNAVAILABLE` compatibility. The scheduler rechecks immediately before running, before review quota reservation.

Before a ledger claim, a refused new request has not started and its unchanged ID can be explicitly submitted after recovery. A refusal after a queued request was claimed is a terminal historical blocked result under the original ID. If even that completion cannot be persisted, reconciliation remains `idempotency_in_doubt`. Neither case permits automatic retries under new IDs.

Normal retained-result accounting is the configured budget plus outstanding operation allowances of 32 MiB. Oversized results are an explicit measured exception: their sole copies remain protected and stop new intake; already admitted finite operations may still finish. This is not a fixed RSS bound. Existing runtime output/resource limits and persistent 32 MiB envelope cap are unchanged; raw and sanitized envelope sizes differ.

Production result-cache writes use asynchronous atomic private temporary files and rename. Initial writes happen on completion. The existing maintenance tick retries at most one protected record, without overlapping an active write, using backoff capped at ten ticks. Recovery from multiple failures can therefore take multiple minutes at the default 60-second tick. No model retry or credential fallback occurs. Crash-orphan temporary-file cleanup remains a pre-existing limitation.

Shutdown adds at most two seconds for result drain after operations settle. It waits for pending writes and attempts at most one final retry, then reports `resultDurability` with `lossRisk` and protected counts. A real monitor with protected results returns `disposed:false` / `PI_RESULT_DRAIN_UNSAFE`: the admin stop and CLI signal paths refuse automatic exit and keep the reader, ledger and existing maintenance cycle alive. Intake remains closed. After persistence recovers, the operator can explicitly request shutdown again. Legacy injected monitors without a drain interface report unknown durability. Forced termination can still lose RAM-only copies; restart preserves fail-closed uncertainty.
