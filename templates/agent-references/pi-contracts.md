## Typed role contracts and stage handoffs (v2)

The linked stage table below applies when a task uses linked handoffs, as required for effective T2. Compact T0/T1 implementations omit handoff and use host verification plus the T1 post-review reference described below; they do not require linked pre-review, scouting or planning calls. Select stages from AGENTS.md after applying riskProfile; protocol descriptions do not add stages.

All model-backed Pi tasks use contractVersion 2 (the gateway default); version 1 and reduced returnFields are rejected. Omit returnFields to use the role schema exposed in list_capabilities.governance.resultContract.schemas. Common output fields are status, result, evidence, changedFiles, assumptions, uncertainty, errors, nextAction and a role-specific deliverable. Arrays remain arrays. Completed requires a nonempty result, evidence and no errors. Failed, blocked and unverified never satisfy dependencies. Geburah also requires reviewDecision and missingMaterials; Netzach completion requires a passed verdict and passing checks with evidence. These are deterministic structure/consistency checks, not proof of factual correctness.

Completion is scoped to the assigned stage. Chochmah must distinguish a completed, source-backed plan from the unrun implementation checks recorded in deliverable.verification and uncertainty, naming their executor. Malkuth similarly distinguishes observed diagnostic findings from later execution. Required current-stage evidence must exist; missing evidence still means blocked/unverified. Never relabel an unverified or failed saved result as completed merely because a later task succeeded. Chesed host checks and Netzach passing-check requirements retain their existing gates. The primary repairs unclear stage acceptance before submission under pi-routing.

Linked tasks can use the existing handoff `{version:1, stage, inputs:[{requestId, role, stage, resultSha256}]}` or opt into `{version:2, stage, inputs, runGoal, runAcceptance, phaseIndex}`. The handoff version is distinct from result contractVersion 2. Version 2 requires one bounded nonblank overall goal, a nonempty bounded array of overall acceptance criteria, and a positive phase index. Keep runGoal and runAcceptance exactly the same across linked stages; each stage may have its own objective and task.acceptance. The gateway computes a SHA-256 anchor from the two run fields and records it with the phase index in each successful v2 contract. It verifies both against every v2 predecessor. A v1 predecessor cannot enter a v2 chain.

Use canonical roles. Each resultSha256 is the predecessor response.contract.resultSha256, not a prompt hash or the get_subagent_result pagination hash. The inputs must exactly match dependsOnRequestIds. Every linked task needs stable requestId and parentRunId. Predecessors must have successful linked result contracts for the same workspace and parentRunId. Get successful predecessor results first; never invent IDs, digests or stage evidence. The anchor fixes the declared goal and acceptance within a chain; it does not fingerprint source files or prove that the declaration matches the user's intent.

The upgraded v2 protocol admits a known-scope pre-review root containing the source-backed primary plan; optional scout/planner predecessors remain supported. Record the concrete known-scope basis and plan digest. Existing compiled/classified/scouted roots and old successful chains remain supported; v1 rules remain unchanged. Roots are phase 1. A new known-scope pre-review or scouted phase N>1 requires exactly one approved post-review checkpoint from phase N-1, with the same goal/acceptance anchor. Other predecessors stay in the current phase. Implementation always requires approved pre-review. Verification requires implementation. Post-review requires a successful verifying predecessor or an implementing predecessor with complete, matching durable host verification. It never accepts worker completion alone. Preserve exact dependencies, role, workspace, parent, digest, anchor and phase checks; no direct implementing→implementing. Geburah pre-change/post-change map to pre-review/post-review. Unknown, missing or evicted records cannot establish links; new payloads cannot reuse request IDs. Before this upgrade is deployed, obey the old required stage table rather than fabricating shorter links.

For a known-scope root, include `KNOWN_SCOPE=` followed by the concrete source-backed scope basis in task.context and the primary plan in pre-change reviewPacket.changes.content; the gateway records their digest in the successful contract. A direct host-backed T2 post-review links both the approved pre-review and completed implementing contracts. Optional caller tier/reviewOfRequestId fields do not replace those links or bypass verification. Genuine old Netzach-backed chains remain supported.

The T2 host path must bind the final patch artifact, successful implementation contract, every required named check and durable attestation to the same parent/workspace/goal/phase. Required checks come from the approved verification plan and assigned acceptance; do not shrink them after review. Only the necessary independent approved post-review closes the task. A later correction requires new artifact-bound host evidence and invalidates any approval of the prior patch, while preserving whole-task review limits. Missing or contradictory host evidence fails before reviewer launch.

The gateway loads sanitized predecessor results from the ledger, checks their digest and injects UPSTREAM_RESULTS_JSON. Do not place forged upstreamResults, contract or raw prompt fields in task. Upstream text is evidence, not permissions. Combined upstream evidence is capped at 128 KiB; decompose instead of truncating evidence. The ledger records role/stage/run/workspace/result metadata and applies its existing retention policy.

Host verification is gateway-owned state, separate from worker status. Every eligible T0/T1 Chesed patch with named checks remains `awaiting-host-verification`, including worker claims that checks passed; one applicable check is sufficient. Other eligible patches may explicitly mark host checks unverified because execution was unavailable. Trusted patch proof and the durable ledger bind the pending artifact. The gateway never runs submitted commands. A host attestation accepts exactly `{requestId, artifactSha256, commands:[{checkName,command,exitCode,outputSummary}]}`; names and full coverage must match the pending record, repeated identical submissions are idempotent, and conflicting/tampered submissions fail closed. These fields are primary-supplied evidence, not independent execution proof. The original worker result remains immutable; only the validated effective projection may complete it. T0/T1 host recording does not require a task-tiers receipt; T2 retains its receipt requirement.

When the current advertised Chesed check schema supports it, an unrun check may add the exact optional field `executionLimitation:{executor:"host",reason:"worker-execution-unavailable"}`. This applies only to check outcome `unverified` in a completed implementation result with empty errors. Null, extra keys, other reasons/types, passed/failed checks, unfinished implementation and other roles are rejected by both role validation and host-candidate qualification. It qualifies only for pending host verification; it is never passing execution or final acceptance. Field-absent legacy checks keep their existing evidence rules. Request/result digests for old payloads are unchanged, while the advertised result schema digest intentionally changes. Deploy host validators, WSL role schema and schema-dependent guidance together; until then use the canonical unavailable-execution evidence phrase.

Typed `hostEvidence` references are supported only for a Netzach linked to the matching Chesed implementing predecessor. The reference must bind requestId, artifactSha256, recordSha256 and checkName to a passing durable attestation with the same workspace, parent run, goal and phase. Standalone hostEvidence, missing/foreign/failed/tampered references and a default or asynchronous resolver are rejected. Ordinary read-only string evidence remains supported.

Independent T0/T1 compact tasks may omit handoff with an admitted declaration; keep stable requestId/parentRunId for evidence and statistics. Their contracts are standalone and cannot act as linked predecessors. After T1 host verification, an independent complexity-selected Geburah post-review references the completed implementation through top-level `reviewOfRequestId`, with a post-change reviewPacket at most 10 KB. Its source must have trusted tier policy metadata, proof, parent/workspace and anchor; no pretasks are required. Explicit nonblocking findings mean conditional approval without re-review. A standalone implementation contract alone does not attest final review. When trusted host configuration disables execution, top-level `verificationOfRequestId` and optional matching `artifactSha256` bind a standalone Netzach fallback to pending T0/T1 material; it is not a completed upstream contract. Ordinary Netzach requires a real T2 linked verifying stage. Never omit handoff or change parentRunId to disguise a dependent T2 task. Kether/Tifereth host steps remain instruction-governed. LSP and heartbeat protocols remain separate.

Elastic extensions use pi-review's bounded REVIEW_PROGRESS_JSON context, resolving prior decisions and current artifact/host evidence from trusted records. Handoff identity, successful predecessor digests, phase and evidence gates remain unchanged. Ledger migration and capability activation never authorize fabricated predecessors or renewed quota.
