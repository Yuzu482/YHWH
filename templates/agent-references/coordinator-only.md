# Pi execution and primary ownership

These descriptions apply to Pi gateway calls, which still enforce their advertised routing, tier, review and ledger rules. They do not govern ordinary direct host work. Existing bound historical maintenance records remain subject to their own host requirements and explicitly user-authorized quotas. Follow higher-priority instructions and the current user request; preserve existing task identities, quotas and history. A topic or receipt does not grant authority.

## Explicit native-host admission

For the explicitly scoped historical native maintenance record, a user-authorized migration may use a separately provisioned direct-host adapter only with its operator-reviewed, external, exact-workspace policy pinned by SHA-256. This branch does not provide that adapter or grant its admission. Its legacy rules do not define the primary host's general coding permissions. No project-discovered configuration, environment switch, unavailable-worker fallback or disabled worker enforcement selects this path. The legacy headless runner remains strict-blocked.

The historical native adapter retains its host-owned risk profile, original parent/goal anchor, one writer, complete source scope, real named command observations and applicable independent review requirements. Reviewers do not edit; author and reviewer sessions differ. The adapter shares the configured Pi review-attempts directory and cannot reset attempts through a route change. Native acceptance is explicitly a host observation record, never `task_accepted` or Pi sandbox evidence. Uncertain cross-ledger transitions block pending explicit reconciliation. Concurrent native/Pi writers are forbidden by coordinator policy; the native active-task record does not provide a cross-backend OS lock.

This source path grants no installed/global policy change, new host permission, external action, credential access or deployment. Pi calls follow the gateway constraints below; direct host work follows current host instructions and user authorization.

Astra owns intent, scope, authorization, reasoning, architecture, decomposition, scheduling, integration and evidence-based acceptance. For Pi implementation tasks, Chesed workers normally use openai-codex/gpt-6.1-terra with task-proportional effort; small, well-defined code tasks may explicitly use Luna (pi-routing). Primary implementation outside Pi is governed by current host instructions and user authorization. These ownership rules do not change higher-priority permissions or reviewer bindings.

The primary may inspect and implement directly when allowed by current host instructions, and may inspect and apply worker-authored patches after scope/base checks. General analysis/policy/deterministic checks need no ceremonial model call. Tightly coupled work uses one bounded writer; parallel writers need disjoint ownership/independent acceptance. Delegation follows current host instructions and the user request. External actions/credentials keep their authorization boundaries.

## Dispatch
1. Query capabilities; cwd must be within roots. Use canonical roles. Define one observable behavior, stable request/run ID, explicit scopes/exclusions/dependencies and necessary tests, normally <=3 write/8 read files. Explain coupling, never split to lower tier. Criteria name trigger/input, result, stable check, method, owner and failure cases. Assign host checks when worker execution is unavailable; record complexity and choose effort under pi-routing/task-plan. Preserve pinned model/provider.
2. Classify whole goal under AGENTS.md/profile; task-tiers is for boundaries. Primary plans known scope; scout/planner is conditional. T2 needs approved independent pre-review; T0/T1 explain why no pre-review. Never label a review passed when unavailable or fabricate linked evidence for standalone compact tasks.
3. Choose advertised resources fitting admission, bounded scope/output. Distinguish queue/execution before revising budget; never reduce host reserve/safety limits or change route to evade a failure.
4. T0 may dispatch synchronously; T1/T2 submit asynchronously. No repeated status/result/sleep-query loops, including hidden scripts. Use an actual completion wait, otherwise independent work/query-free waiting until genuine event, declared deadline or user request. Retrieve terminal results with pagination/digest verification under pi-results; pending does not authorize polling.
5. Check correct role/provider/model, successful process/cleanup, scope/base and real patch. Mechanically apply acceptable authored material; run focused host checks and retain actual output/exits. Unverified solely because execution was unavailable may deliver a usable patch; blocked is eligible only under existing T2 conditions. Actual errors remain incomplete. Passing host tests do not prove independent review. Worker repairs require exact evidence and rerun host checks.
6. Record tier/declaration, request/role/model, files/artifact, outcome, host evidence and review independence. T0 uses host verification; T1 non-diff ≤ 8 KiB, total ≤ 24 KiB (serialized UTF-8); over budget organize complete reviews by commit without resetting whole-goal tier/quota, nonblocking findings conditional/no re-review; T2 pre/post. pi-review controls activation and whole-goal elastic counts/time/progress. All tiers may record artifact-bound host checks. Netzach is for unavailable host execution or a concrete independent execution need. Queue cancellation/blocked admission/heartbeat/probes/deterministic calls/result retrieval are separate from actual model executions.

## Repairs and acceptance
Initially <=3 implementation calls including zero-launch; tighter user bounds apply. Diagnose exact error/exit/output, base and paths before repair; retain goal/acceptance/review budget. No unchanged retry, access switch or failure relabel. At bound stop/reassess. Scoped repairs need no renewed permission; ask for new authority/scope/risk/budget or exhausted review only. Repeated failures require concrete host diagnosis before any scoped retry; preserve original goal, history and review budgets. Existing host bounds remain. When the deployed gateway advertises milestone admission, follow pi-contracts for exact failure diagnoses and pi-results for explicit closure; never bypass them by changing request identity.

Initial production changes to stages/dependencies/identity/ledger/host evidence/final acceptance require full regression. Later repairs use impact checks. Reuse needs explicit origin plus unchanged production/test/dependency/config/environment/runtime fingerprints; otherwise rerun. Never label reused results new execution or submit old exits as fresh host commands. Required names remain; changed artifacts invalidate prior attestation/review, never reset quotas.

For small fully supplied changes, access:none may return an explicit worker patch/exact replacements. This proves authorship/delivery only, never file mutation/tests. Include real necessary source context, omit read/writeScope, report changedFiles/unrun checks. Use read/workspace-write when actual file access is needed. Never use none to evade rejected disclosure or hide failed/uncertain writes.

## Unavailable workers/reviewers
If Pi is unavailable/blocked/timed out/unusable, continue authorized direct work when permitted by the current host and user. Reconcile possibly executed writes using original identity and real patch/workspace before any new attempt. Proven queued zero-execution cancellation may be replanned with suitable resources/new documented ID. Do not interpret Pi availability as a grant or denial of host permissions.

Reviewers keep their separate pinned role/provider/access:none. Never send private materials after an approval rejection, relabel worker as reviewer, or claim host self-review independent. Report unavailable independence without changing owner. Host rules govern arbitrary editors/shells; gateway metadata/heartbeat alone does not prove compliance. Verify worker provenance and accepted patches. Policy changes alone authorize no restart/deploy/release/push.

## YHWH maintenance work in progress
Keep at most one active unmerged maintenance work line. A successor waits for merge, deployment and installed checks, or explicit retirement with preserved evidence. Frozen deferred proposals cannot be parallel writers and are not completed work. Candidate rules never decide their own admission or acceptance.
