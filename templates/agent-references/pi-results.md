## Async result acceptance and review timing

### Strict no-polling policy for Astra (user decision 2026-09-21)

Astra must not repeatedly poll Pi tasks. Do not run timed get_subagent_status, list_subagents or get_subagent_result loops for the same active requests, including sleep-then-query loops, repeated 50/60-second batches, or loops hidden inside functions.exec, shell scripts or background helpers. This is a prohibition, not a suggestion to poll less frequently. It supersedes the earlier tool-side aggregation and 60-second fallback permission. Render the monitor at most once per task group when useful; its independent UI refresh and Pi's deterministic supervisor heartbeat do not require Astra to inspect each update.

Prefer the authenticated `wait_subagent` completion-event tool for the same Pi request IDs (or `gateway-client wait <request.json>` with `{ "requestId": "...", "timeoutMs": 55000 }`). It waits once for at most 55 seconds, returns compact terminal metadata, and neither starts nor replays execution. Its timeout/abort stops only that wait; it never cancels the task. If unavailable, status/result reads remain immediate, not event subscriptions, and another host's wait_threads does not accept Pi request IDs. Do not claim a missing wait interface exists. Preserve asynchronous submission, cancellation, request-ledger reconciliation and role bindings rather than switching execution routes to avoid waiting.

If no completion-wait tool exists, do useful independent work or wait without status queries until a predeclared queue/execution deadline, a genuine completion/failure/cancellation signal, or an explicit user status request. Do not invent a completion notification or promise zero host/model turns. At that decision point, perform one necessary status/result read and act on it. A not-ready result is not permission to start another polling loop; retain the same request ID and the original deadline. A timeout by itself never authorizes task replay or cancellation.

Necessary reads are limited to explicit user questions, externally observed state changes, deadlines, cancellation/recovery decisions, and a finite predeclared acceptance measurement. Do not relabel routine polling as validation. Full terminal-result pagination and recovery from a failed transport read remain allowed and must not redispatch work. Required host progress updates still apply, but they must not cause extra status calls or repeated unchanged JSON. UI refreshes and local supervisor heartbeats are not worker model calls; token savings remain unmeasured.

Use submit_subagent for review and T1/T2 delegated work; compact T0 may use a synchronous dispatch. get_subagent_status reports progress, not the full evidence. When terminal, call get_subagent_result with requestId. Require ready=true; then check state, result.ok, formatValidation and structuredResult/reviewValidation. For large responses concatenate resultJsonChunk pages by nextOffset and verify the SHA-256 of the reconstructed UTF-8 JSON before parsing. Offsets are JavaScript UTF-16 units. Redaction precedes pagination. Ordinary live monitor results may be evicted with old terminal entries; RESULT_NOT_FOUND does not authorize repeating a write task. Reconcile writes through the persistent ledger. A task in `awaiting-host-verification` is terminal for worker execution and retrieval, but is not successful, does not satisfy dependencies, and has no successful contract until the durable host record projects it as completed.

On the upgraded host path, the same artifact-bound record_host_verification mechanism can support T2 post-review without a model merely repeating host logs. Preserve the same required checks and linked implementation identity; the post-review gate and final task_accepted event remain necessary. A changed patch cannot reuse old verification/approval. Evidence reused for impact-based acceptance is separately labeled with origin and unchanged-input fingerprints; host attestation commands describe actual current execution only.

For an eligible pending patch, read `list_host_verification_pending` and use only its exact requestId, artifactSha256 and required check names. Run the host checks, then submit `record_host_verification` (or `gateway-client record-host-verification <evidence.json>`) with exactly `{requestId, artifactSha256, commands:[{checkName,command,exitCode,outputSummary}]}`. T0/T1 need no task-tiers receipt; T2 needs a fresh one. The CLI may fetch and retry only after explicit zero-mutation WORKFLOW_TOPIC_REQUIRED for legacy/T2 compatibility. The gateway records evidence and never executes commands. All required names must appear exactly once; one applicable check is valid. Identical repeats are idempotent; conflicting results cannot overwrite the durable attestation. A nonzero check projects to failed without success contract. Command/output fields are caller assertions, not independent execution proof. Pending results remain restart-visible; dependent handoffs wait for completed projection and validate the contract digest.

For nontrivial reviews, Tifereth should prefer standard resources with up to 300 seconds when admission permits, keep the pinned model/thinking, and submit one independently reviewable change per material packet. Tiny format probes can use small. Never omit required review evidence to fit the budget. Inspect authenticationMs, startupMs, timeToFirstResponseMs, firstResponseSource, generationMs, processTailMs and cleanupMs. Missing measurements are null, not proof of zero work. Timings are host observations of Pi stream events; timeToFirstResponseMs includes startup and may only observe the completed message when streaming is unavailable. Generation is measured until agent_end, not provider-only GPU time.

Claude API keys have no local expiry-renewal guarantee. Local checks do not validate remote account access; failures require user key repair and an authorized recovery probe.

Review execution counts and time use pi-review's durable whole-goal elastic policy only when advertised by the running gateway. Queue time, zero-launch failures and actual/unknown execution remain distinct; record remaining quota and original review outcomes before escalation. Never reset budget through repair, phase, ID or restart.
