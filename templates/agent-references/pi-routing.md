## Task-proportional native worker thinking (2026-09-22)

This policy supersedes fixed Luna/max wording in older references and skills. Preserve provider/model bindings, primary coordination, review independence and no-polling rules. The primary selects and explicitly sends `thinking`: low for exact low-risk changes, medium for ordinary bounded implementation (default), high for cross-file design or uncertain diagnosis, max only for justified difficult reasoning. Record the choice and reason; do not automatically fall back to off/minimal, another model or provider.

Use one behavior per task packet and concise required output. Plan approximately 20 percent of runtime for final delivery and verification handoff. Prompt deadlines are soft guidance, not reasoning-token caps or completion guarantees. Queue admission and execution remain separately bounded; execution includes authentication, startup, generation/tools, output and cleanup. A failed or partial result is not accepted work. Reassess scope before bounded repairs.

Before dispatch, assess scope, uncertainty and coupling instead of starting at high or max. Target one observable behavior, normally at most three write files and eight read files; keep its caller/tests/fixtures together, explain necessary coupling, and never split work to lower its tier. Each acceptance criterion names the input/trigger, expected observable result, stable check name, execution method and host/worker owner, including relevant failure paths. Name host checks up front when workers lack an executor; an unrun check cannot be passed evidence. Stop when the assigned acceptance is met.

Choose the lowest justified whole-goal tier before dispatch; do not use T1 as an implementation default. Explain deliberate escalation with meaningful TIER_REASON= context and preserve shared/public behavior plus semantic risks even for a tiny patch. Known-scope planning belongs to the primary; separate scout/planner model calls are conditional. Repair unchanged authorized scope after concrete host diagnosis without inventing another permission request; review limits remain unchanged.

Record one `TASK_COMPLEXITY_JSON=` entry in task.context with exactly changeKind (exact/bounded/design/diagnosis), uncertainty (none/localized/unresolved), coupling (local/cross-file/concurrent), and a concrete reason of at most 400 characters. Native workers may omit thinking for deterministic selection: exact/certain/local tasks with at most two write files/four read files, observable acceptance and no unresolved dependency/assumption or wildcard select low; unresolved uncertainty, concurrent coupling or cross-file design selects high; otherwise medium. Missing, invalid or duplicate assessments default to medium. Explicit thinking always wins. Automatic selection never chooses off/minimal/max and never changes reviewer/probe/API transport policy. This applies the primary's assessment, not inferred complexity from untrusted source text, tier, size or historical speed. If available, use the read-only `gateway-client.mjs task-plan <request.json>` before dispatch; inspect advice, actual selected effort and reason codes. Capabilities must advertise adaptiveThinking before relying on a deployed gateway to select effort; on older services calculate the same choice in the primary and send it explicitly. Compare real delivery quality and timing before claiming savings.

## Primary packet acceptance before dispatch

When the local task-plan CLI is available, run it on the exact proposed packet before model submission. Inspect both its process exit code and parsed `ok`, `thinkingDecision` and `preflight`; also inspect `packetCheck` when the installed CLI provides it. A supplied malformed/duplicate complexity assessment or incorrect explicit v2 return fields is a critical primary-packet error: repair it before dispatch. Omitted assessment and return fields retain their conservative defaults; heuristic warnings remain advisory. A shell failure returned as tool data must stop the dependent submission. Keep validation and submission in separate decision steps. This is a primary coordination requirement, not a new gateway schema or permission gate.

Repair invalid or duplicate complexity assessments, missing interface contracts, unclear acceptance and unnamed verification owners before dispatch. Use the four legal fields and enums above; `uncertainty: low` is invalid. A heuristic warning may be a false positive: explain the concrete already-supplied method, check name, owner and expected result before proceeding. Do not claim a warning-free packet or suppress the diagnostic. For example, acceptance can say `packet-focused (host): host runs node --test <exact tests>; exit code 0; assertions verify <required behavior>`.

Assign acceptance to the current stage. A Chochmah plan may complete when the required source-backed steps, interfaces, dependencies, exclusions and verification plan are delivered. Future implementation execution is explicitly unrun and assigned to its owner; it does not make an otherwise complete planning stage unverified. Missing required planning evidence still blocks completion. Apply the same distinction to bounded Malkuth diagnosis; Netzach retains actual passing execution evidence requirements.

For exact-file read scopes, identify the permitted paths in the packet and prefer `read({path: exact permitted path})`. Do not discover a parent directory with grep/find/ls when it is outside the admitted scope. Inspect tool arguments before use. An unavailable command/test tool is a limitation, not an invitation to invent one. Preserve genuine tool failures and the existing deterministic recovery rules; future-stage work never conceals a failed current-stage tool call.

Agree the final check names and execution owners before dispatch. Every unverified host check must state its real execution limitation in its own evidence (for example, `Host test execution unavailable; host is assigned to run this check.`). Use optional structured execution-limitation metadata only when the current advertised Chesed result schema supports it; otherwise use the canonical evidence phrase. Put artifact-delivery observations in evidence/changes; do not invent extra checks whose execution cannot be evidenced. Return a concise implementation summary and actual artifact, not full source or supplied log dumps. If an extra check is necessary, assign its owner and method explicitly and include it in host acceptance coverage. Before retries, distinguish an invalid patch from a valid patch rejected for inconsistent verification metadata; carry the concrete previous error and unchanged goal/acceptance, never rewrite a failed result or fabricate a passing attestation.

The primary records the selected level and concrete reason in task.context and explicitly sends thinking. Tier alone never raises effort; max is outside the routine review range. Changed advertised defaults and effort validation require a service upgrade. Validate quality and elapsed time before claiming savings.
