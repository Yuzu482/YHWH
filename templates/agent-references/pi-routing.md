## Primary packet acceptance before dispatch

When the local task-plan CLI is available, run it on the exact proposed packet before model submission. Inspect both its process exit code and parsed `ok`, `thinkingDecision` and `preflight`; a shell failure returned as tool data must stop the dependent submission. Keep validation and submission in separate decision steps. This is a primary coordination requirement, not a new gateway schema or permission gate.

Repair invalid or duplicate complexity assessments, missing interface contracts, unclear acceptance and unnamed verification owners before dispatch. Use TASK_COMPLEXITY_JSON fields changeKind (exact/bounded/design/diagnosis), uncertainty (none/localized/unresolved), coupling (local/cross-file/concurrent), and reason (a concrete explanation of at most 400 characters); `uncertainty: low` is invalid. A heuristic warning may be a false positive: explain the concrete already-supplied method, check name, owner and expected result before proceeding. Do not claim a warning-free packet or suppress the diagnostic. For example, acceptance can say `packet-focused (host): host runs node --test <exact tests>; exit code 0; assertions verify <required behavior>`.

Assign acceptance to the current stage. A Chochmah plan may complete when the required source-backed steps, interfaces, dependencies, exclusions and verification plan are delivered. Future implementation execution is explicitly unrun and assigned to its owner; it does not make an otherwise complete planning stage unverified. Missing required planning evidence still blocks completion. Apply the same distinction to bounded Malkuth diagnosis; Netzach retains actual passing execution evidence requirements.

For exact-file read scopes, identify the permitted paths in the packet and prefer `read({path: exact permitted path})`. Do not discover a parent directory with grep/find/ls when it is outside the admitted scope. Inspect tool arguments before use. An unavailable command/test tool is a limitation, not an invitation to invent one. Preserve genuine tool failures and the existing deterministic recovery rules; future-stage work never conceals a failed current-stage tool call.

Agree the final check names and execution owners before dispatch. Every unverified host check must state its real execution limitation in its own evidence (for example, `Host test execution unavailable; host is assigned to run this check.`). Put artifact-delivery observations in evidence/changes; do not invent extra checks whose execution cannot be evidenced. If an extra check is necessary, assign its owner and method explicitly and include it in host acceptance coverage. Before retries, distinguish an invalid patch from a valid patch rejected for inconsistent verification metadata; never rewrite a failed result or fabricate a passing attestation.
